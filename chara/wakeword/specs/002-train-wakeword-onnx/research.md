# Research: обучение wakeword и отчёт

Дата: 2026-11-09. Решения приняты по текущему коду feature 001 и закреплённому source.ipynb; runtime-код в этом этапе не меняется.

## 1. Основа обучения

**Decision**: Перенести алгоритм клеток 28 и 30 source.ipynb (SHA-256 434603fa67d1a340e392c04d1e5754e88bc20b703c8a587f5ea4ac6fb8cdf6ca). Модель: Flatten → Linear(1536,128) → LayerNorm(128) → ReLU → Linear(128,1). Обучение возвращает logits, экспортная обёртка добавляет sigmoid.

**Rationale**: Это фактический классификатор notebook, а не иной trainer с похожим названием. Генерация Parler/Vosk и локальная подготовка feature 001 уже работают и не переписываются.

**Alternatives considered**: вызов плавающего upstream auto_train (другой контракт, не воспроизводит исправленный рецепт); новый классификатор (изменяет цель переноса); добавление обучения в BrainBox (противоречит согласованному host-side выполнению).

## 2. Стадии, sampling и журнал

**Decision**: Production: stage_steps=[20000,2000,2000], learning rates=[1e-4,1e-5,1e-6]; Adam создаётся заново для каждой стадии. Batch 32 positive + 32 adversarial negative + 64 ACAV; выбор с возвращением. ACAV train: случайная строка и окно из 16 кадров. Веса negative линейно растут от 1 до 1500; если минимум window FP/hour по всей истории выше 0.5, предел удваивается после стадий 1/2. Сохраняется исходная политика warmup/hold/cosine и hard mining: negative score≥0.001, positive score<0.999. Порог валидации по умолчанию 0.5, настраивается.

История различает глобальную итерацию sampling и фактический optimizer update. Weighted BCE записывается только при update вместе со стадией, LR, negative weight, числом retained examples и временем. Пропущенные update учитываются отдельными счётчиками, не заполняются вымышленным loss. Для accumulated hard examples сохраняется целевой объём 128; непустой остаток в конце стадии явно flush-ится, а отличие от notebook (который его теряет) отражается в run metadata. Учёт графов не должен нарушаться промежуточной валидацией.

Smoke: stage_steps=[8,4,4], batch_counts=[2,2,4], accumulation_examples=8, max_negative_weight=10. Минимумы по 2000 шагов не применяются скрыто. Нужны ≥1 реального update и ≥1 validation event; иначе запуск незавершённый, с причиной. Обе конфигурации используют один trainer.

**Rationale**: Сохранить смысл curriculum и получить быстрый настоящий CPU smoke. Тестовые данные не дают обещаний о качестве.

**Alternatives considered**: одно число steps с неявными минимумами notebook (непригодно для smoke); loss по sampling iteration (не соответствует обновлениям); молчаливое отбрасывание accumulation remainder (теряет примеры и измерения).

## 3. Большие данные и границы фоновых сегментов

**Decision**: Все NPY читаются через mmap, конечность проверяется чанками; на устройство передаются только партии. Supervised input=(N,16,96), background train=(N,T,96), T≥16. Background validation feature 001=(M,96); длина исходной строки T берётся из проверенной пары ACAV train/val одного resource manifest, M должно делиться на T. Для импортированного фона без такого происхождения нужны явные segment lengths и frame_step_seconds; выдумывать их нельзя.

Валидационные окна создаются отдельно внутри каждого сегмента, stride=1 frame. Для сегмента длиной L учитываются все L-16+1 окон. Окна, пересекающие границы независимых исходных ACAV rows, исключаются. Внутри каждой validation event и финального измерения применяется один и тот же порядок. Ничто не материализует все перекрывающиеся окна целиком. На диске сохраняется компактный порядок сегментов и окон, позволяющий восстановить индекс каждого score.

**Rationale**: Notebook делает off-by-one M-16 вместо M-16+1 и после flatten создаёт искусственные окна через границы строк. Это ошибки, которые не надо переносить; исправление меняет абсолютное число фоновых FP и обязательно указывается в отчёте.

**Alternatives considered**: полная contiguous копия sliding windows (многократный расход RAM); сохранение пересекающих границы окон ради побитной имитации (метрика относится к искусственным стыкам).

## 4. Значение FP/hour

**Decision**: Сохранить исходный тип измерения как proxy: threshold_windows_per_feature_hour = background_positive_windows / feature_equivalent_hours, где feature_equivalent_hours = оценённые кадры × 0.08 / 3600. Оценённые кадры — кадры валидных сегментов, участвующих в проверке; их число, число окон, границы, hop и исключённые короткие сегменты сохраняются. Для стандартного подготовленного ACAV каждый сегмент длиной ≥16 участвует целиком.

В отчёте подпись: «Пороговые окна/ч по времени признаков (не независимые события)». Рядом приводятся raw count, feature-time exposure, stride и отсутствие event grouping. Настоящая waveform duration хранится отдельно и остаётся null, если нет временного происхождения аудио; proxy не представляется реальными часами прослушивания. TARGET_FP_PER_HR notebook переименовывается в target_window_fp_per_hour в настройках адаптации весов. Независимый событийный FA/hour и ROC на реальном непрерывном аудио не добавляются без соответствующих данных.

**Rationale**: Из отдельных embeddings нельзя честно восстановить реальную длительность аудио и независимые активации. Но можно повторяемо пересчитать исходную оконную метрику с явной методикой.

**Alternatives considered**: считать каждое окно пользовательским событием; объединять события с придуманным cooldown; объявлять физическую длительность по числу строк NPY. Все три искажают смысл измерения.

## 5. Checkpoints и итоговое состояние

**Decision**: Начиная с третьей валидации сохранять кандидата при n_fp≤p50 всей истории и recall≥p5 всей истории, включая текущую оценку. Финальный отбор среди кандидатов: accuracy≥p90, recall≥p90, window FP/hour≤p10. При пустом пересечении выбрать минимальный window FP/hour, затем максимальный recall, затем наиболее ранний validation event как детерминированный tie-break. При отсутствии кандидатов использовать последнее реально обученное состояние. Кандидаты сохраняются на диск; отбор содержит ID, метрики и хеши. Усредняются веса выбранных состояний; финальные метрики checkpoint mean не публикуются как метрики модели.

**Rationale**: Соответствует cell 30 и позволяет объяснить происхождение результата, в том числе короткого smoke.

**Alternatives considered**: последнее состояние всегда (теряет selection); лучшие значения разных checkpoints в одной строке (такой модели не существует).

## 6. ONNX и финальные измерения

**Decision**: Сохранить torch 2.2.2+cpu/onnxruntime 1.17.3; добавить onnx==1.16.1 и явно закрепить используемый renderer графиков. По PyPI доступны wheels ONNX 1.16.1 для Windows cp311/cp312; runtime установка/export проверяются в реализации. Экспорт legacy torch.onnx.export, opset 14, без dynamo=False: проверенная локальная сигнатура torch 2.2.2 такого аргумента не имеет. Batch-axis динамический; имена как в source: onnx::Flatten_0 и output, float32 (B,16,96) → (B,1).

До публикации: onnx.checker.check_model, ORT CPU load/run, batches 1 и >1, finite/range; parity atol=1e-5, rtol=1e-4. В parity идут положительные/отрицательные validation-примеры и детерминированная выборка background до 256 окон; ID выборки и максимальная ошибка сохраняются. Итоговые метрики и scores вычисляются именно ORT на всех валидационных входах; равенство классов на пороге не предполагается из одного лишь допуска raw scores. После усреднения всё оценивается заново.

**Rationale**: Notebook печатает stale ACAV FP/hour из history после averaging, что не характеризует экспортированный файл. Структурная проверка не заменяет фактический запуск и parity.

**Alternatives considered**: увеличить весь torch-stack ради одного параметра; публиковать метрики последнего checkpoint; проверять только загрузку ONNX.

Источники: [ONNX checker](https://onnx.ai/onnx/api/checker.html), [ORT Python API](https://onnxruntime.ai/docs/api/python/api_summary.html), [ONNX 1.16.1 metadata](https://pypi.org/pypi/onnx/1.16.1/json). Точное поведение training/export дополнительно сверено с локальной torch 2.2.2 и pinned notebook; современные docs не подменяют эту версию.

## 7. Отчёт и первичные результаты

**Decision**: HTML report.html, встроенные SVG, без CDN. Matplotlib Agg (уже присутствует в host lock) делает графики реальных train loss/update и validation recall/accuracy/window FP/hour на отдельных осях. При одной точке — маркер, не выдуманная кривая; сглаживание не требуется в первой версии. html.escape для текстовых полей. Обязательный порядок: валидация итогового ONNX → история обучения → данные.

Primary artifacts: metrics.json, history.jsonl, checkpoint-selection.json, data-snapshot.json, scores/*.npy, export-check.json. Scores хранятся в исходном порядке по отдельным наборам, background — mmap vector. Precision при TP+FP=0 становится null с причиной; F1 считается напрямую 2TP/(2TP+FP+FN), при валидном положительном классе знаменатель ненулевой. Report-only читает эти файлы, проверяет связь с model SHA и не запускает inference/training.

**Rationale**: Числа проверяемы и отчёт можно восстановить без дорогих этапов.

**Alternatives considered**: отчёт только из агрегированной console history; внешние картинки/JS; восстановление отсутствующих чисел приблизительными оценками.

## 8. Интеграция и повтор

**Decision**: training/ — отдельный пакет рядом с generation/, корень остаётся тонким. Сохранить существующий Python generation.run и добавить run_training/run_full. Make run становится полным циклом; make generate явно оставляет прежнюю подготовку данных, make train работает с существующим DATASET без BrainBox, make report восстанавливает HTML. Конфигурации генерации и обучения раздельны. Full output содержит generation/, training/ и full-run.json; model/report находятся в training/. Повторный синтез уже готового датасета не требуется.

Собственные config fingerprint и состояния обучения проверяются до кэша Chara. Сохранённые итоговые stages можно переиспользовать после сбоя экспорта/отчёта. Автоматического resume незавершённого optimizer loop в первой версии нет: partial training сохраняется и требует нового OUTPUT, а не молча запускается заново. Готовая модель при восстановлении report не меняется.

**Rationale**: Не смешивать generation complete с training/full complete и не затрагивать работающую генерацию.

**Alternatives considered**: добавить обучение внутрь generation.run (ломает прежний контракт); помещать все этапы в один Chara root (смешивает независимые cache fingerprints); переобучать при удалённом HTML.
